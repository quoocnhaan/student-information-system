# Direct API job publishing plan

## Goal and scope

After `upload_pdf` saves a PDF and a `queued` OCR job, the knowledge API starts a direct RabbitMQ publish and returns `202` without waiting for RabbitMQ. When RabbitMQ comes back after an outage, the knowledge API republishes jobs that are still `queued`. A caught worker error ends the job as `failed`; an individual LM Studio OCR request has a 60-second elapsed-time limit.

This plan supersedes the **dispatch and worker-recovery parts** of `JOB_ROW_DISPATCH_PLAN.md`. Keep `job` as the database record, the existing durable `knowledge.jobs.ocr` queue and `job.queued` routing key, the worker's guarded database claim, and the database live query used to send job progress to API WebSocket clients. Remove only the live query used to wake the **dispatcher**. The WebSocket subscription, its REST fallback, and its separate WebSocket heartbeat are still needed for UI progress.

Accepted limits: no periodic database scan for queued or running jobs, no recovery of an API or worker process that dies, no broker publisher-confirm tracking, and no automatic OCR retry. A job can remain `queued` if the API dies after returning `202` but before publishing and RabbitMQ has no later outage/recovery event. A job can remain `running` if its worker process dies. State these limits in the workflow documentation and surface the current job status to the UI.

## Target flow

1. `upload_pdf` validates and stores the PDF, then commits the document and `queued` job together as it does today. After that commit, schedule a publish attempt in the knowledge API process and return the existing `202` body immediately. Do not make the HTTP response wait for a broker connection, a publish write, or a publisher confirm. If scheduling the in-process attempt itself fails while the API is alive, log it and leave the saved job `queued`.
2. Keep a long-lived RabbitMQ publisher connection in the knowledge API. If RabbitMQ is unavailable, the publish attempt logs the failure and leaves the job `queued`. Connection monitoring and reconnection run independently of upload requests; RabbitMQ protocol heartbeats may be used by the AMQP client to detect a silent broken connection. These are connection signals, not job heartbeats.
3. After a broker outage, once that connection is **established again**, query all `queued` jobs in bounded pages and publish their job IDs to the existing durable queue. Include the case where the API started while RabbitMQ was down and its first connection succeeds when RabbitMQ returns. Complete the scan even if it spans more than one batch. A failed scan or publish should be logged and should leave the job `queued`; the next broker recovery event is the next automatic recovery opportunity. Do not add a periodic scan or a SurrealDB dispatch subscription.
4. A queued job can already have a RabbitMQ message waiting for a worker when a reconnect scan runs. The scan may publish that job ID again. Preserve the worker's atomic `queued -> running` claim so only one delivery starts processing; acknowledge and ignore later duplicate deliveries. New messages need only `job_id`; accept existing `{job_id, dispatch_generation}` messages during cutover, then remove generation handling after the old queue messages are accounted for.
5. On a valid delivery, the worker claims the job, acknowledges the message, and processes it. If processing code raises an exception that the worker catches, persist `job.status = 'failed'`, a useful error, and the document's failed processing state; publish the resulting status to the existing UI path. Do not schedule another job attempt. A normal successful job still ends as `completed`.
6. Bound each LM Studio `/chat/completions` request to **60 seconds of elapsed time**. OCR calls are made once per PDF page, so this is a per-page request limit, not a 60-second limit for the whole PDF. Treat a timeout as a caught processing failure and mark the job `failed`. An HTTPX inactivity timeout alone does not enforce an overall elapsed-time limit; use an elapsed-time deadline around the request.

## Implementation steps

1. **API-owned publisher.** Add the RabbitMQ publisher lifecycle to `src/app/main.py` or a focused API-owned component: start without blocking API readiness while RabbitMQ is down, reconnect when it returns, and close on shutdown. Reuse the queue/exchange declaration and persistent job message in `src/app/infrastructure/rabbitmq.py`. Disable publisher confirms for this path and remove the confirm-timeout/rejection handling. Put the post-commit publish scheduling in `src/app/api/v1/documents.py`. Completion criterion: an upload returns `202` after the database commit even when RabbitMQ is down; a broker outage leaves its job `queued`.
2. **Reconnect recovery.** Add a bounded `queued`-job query to `src/app/infrastructure/surreal.py`. On the RabbitMQ down-to-up transition, scan and publish queued IDs until the scan is exhausted. Serialize recovery scans per API process; multiple API instances may publish duplicate messages, which the guarded worker claim must reject safely. Establish the queue topology before publishing after reconnect. Completion criterion: with the API still running, stop RabbitMQ, upload a PDF, restart RabbitMQ, and observe that its saved queued job reaches a worker without an API restart or periodic DB scan.
3. **Retire dispatch bookkeeping.** Remove `src/app/dispatcher.py`, the `knowledge-dispatcher` Compose service, dispatch-specific metrics/settings/tests, and the database methods used only by the dispatcher. Remove the obsolete dispatch fields and index listed below through an explicit SurrealDB migration; editing `db/schema.surql` alone does not remove definitions already installed in a database. Keep existing queued rows valid throughout cutover. Completion criterion: no running service subscribes to job changes for dispatch and no dispatch timer or publish lease remains.
4. **Make caught worker errors terminal.** In `src/app/worker.py` and `src/app/infrastructure/surreal.py`, replace retry scheduling with a guarded terminal-failure update. Remove the worker's periodic expired-lease sweep, lease-renewal task, and retry/backoff settings and metrics. Keep `worker_id` as the ownership guard for updates from the worker that claimed the job, but do not expire or renew that claim. Remove the obsolete worker retry and lease fields listed below and adjust the job status API/frontend accordingly. Preserve the consumer connection and its RabbitMQ protocol heartbeat. Completion criterion: a caught OCR or processor error produces one `failed` job and one failed document, with no new queue message or scheduled attempt.
5. **OCR deadline.** Set the OCR request limit to 60 seconds in `src/app/config.py`, Compose, and `.env.example`; enforce an elapsed-time deadline in `src/app/infrastructure/ocr.py` around each LM Studio HTTP request. Completion criterion: a request that remains open beyond 60 seconds produces a caught timeout and the worker persists `failed`.
6. **Docs and cutover.** Update the README, workflow/presentation guide, and environment examples so they describe API publish, RabbitMQ recovery scan, caught-error failure, and per-page OCR timeout. Start the new API publisher before removing the dispatcher; verify any already queued jobs are handled by a **one-time cutover backfill** while the broker is available, then stop the old dispatcher. Do not purge the RabbitMQ queue or remove the job-status WebSocket subscription. Completion criterion: the deployed stack has no dispatcher container, existing queued jobs are accounted for, and current status still reaches the UI.

## Exact `job` schema and contract cleanup

- Remove `dispatch_published_at`, `dispatch_publish_attempts`, `dispatch_last_error`, `dispatch_next_publish_at`, `dispatch_lease_owner`, and `dispatch_lease_expires_at`. Remove the `job_dispatch_due` index. They only serve confirmed publishing, dispatch retries, or the dispatch lease.
- Remove `max_attempts`, `next_attempt_at`, and `lease_expires_at`. Remove the `job_claimable` index or replace it with an index on fields still used by the reconnect query; `job_status_created` already indexes status and creation time. They only serve worker retries or lease recovery.
- Remove `attempts` and retire the UI's attempt counter together. Remove `attempts`, `max_attempts`, and `next_attempt_at` from `JobStatusResponse` in `src/app/api/v1/schemas/jobs.py`, its mapping in `src/app/api/v1/jobs.py`, the admin-web contract, and the `Attempt X of Y` display in `JobProgress.tsx`. Update contract and UI tests.
- Remove `dispatch_generation` after the new worker can handle old and new RabbitMQ payloads and all pre-cutover messages have been accounted for. Change new publisher messages to carry only `job_id`; keep the guarded `status = 'queued'` database claim as the duplicate defense. Update the broker parser, worker claim, and tests before dropping the field.
- Keep `status`, `error`, `sequence`, progress fields, `claimed_at`, and `worker_id`. `worker_id` is an ownership check, not a heartbeat or expiring lease.
- Delete these fields from new-job creation, database update methods, the declarative schema, and existing rows through a versioned migration. Remove obsolete indexes and schema definitions in that migration. Preserve data and schema compatibility until the corresponding running API, worker, and dispatcher versions have been replaced.

## Verification

- Upload with RabbitMQ up: `202` is returned from the database commit path and the worker completes the job. The request does not await a broker confirmation.
- Upload while RabbitMQ is down: `202` is returned and the job stays `queued`. Restart RabbitMQ while the knowledge API stays up; the reconnect scan sends that job and the worker claims it.
- Seed more queued jobs than one recovery batch; all are visited. If two API instances scan or a message was already waiting in RabbitMQ, only one worker processing run starts per job.
- Force a caught OCR exception and a request that exceeds the 60-second per-page deadline; each ends in `failed` without retry and is visible through the existing job status endpoint/UI.
- Verify there is no timed job sweep, worker lease renewal, dispatcher subscription, or broker confirm timeout. Verify the API's **status** live query and WebSocket/REST updates still work.

## Explicit tradeoffs

The database still stores a job before publishing, but under this design it does not guarantee that every saved job will eventually reach RabbitMQ. A process death or an unreported publish loss can leave a queued job until a later RabbitMQ recovery event. A worker process death can leave a running job indefinitely. These outcomes match the requested scope; they must not be represented in the UI as successful or automatically failed work.
