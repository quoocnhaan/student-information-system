# Job-row dispatch plan

## Goal

Use `job` as the only durable database record for an asynchronous task, its RabbitMQ dispatch request, and its current progress. SurrealDB live queries on `job` wake the dispatcher and feed live progress to the API's existing WebSocket clients. Keep the existing durable RabbitMQ jobs queue, publisher confirms, generation-guarded worker claim, retries, and worker lease recovery. Remove `outbox_event` after the replacement is running. Live-query notifications are transient; the job row remains authoritative.

This plan replaces the outbox portion of the current knowledge workflow. Preserve the shared queue and routing decisions in `SHARED_JOB_QUEUE_PLAN.md`, including the existing `knowledge.jobs.ocr` queue name and `job.queued` routing key. The current worktree contains changes to job routing and broker code; inspect and preserve those changes during implementation.

## Job fields and invariants

Add these fields to `job` in `db/schema.surql`:

| Field | Meaning |
| --- | --- |
| `dispatch_published_at: option<datetime>` | RabbitMQ confirmed the current `dispatch_generation`; `NONE` means this generation still needs confirmed delivery. |
| `dispatch_publish_attempts: int` | Number of publish attempts for the current generation. |
| `dispatch_last_error: option<string>` | Last publish failure for the current generation. |
| `dispatch_next_publish_at: option<datetime>` | Earliest retry time after a publish failure. |
| `dispatch_lease_owner: option<string>` | Unique token for one publish attempt, not merely a process ID. |
| `dispatch_lease_expires_at: option<datetime>` | Releases a publish claim after a crashed or stalled publisher. |

Initialize a new queued job with generation `1`, `dispatch_published_at = NONE`, `dispatch_publish_attempts = 0`, and the other dispatch fields `NONE`. When `schedule_retry_or_fail` schedules another attempt, or `requeue_expired_jobs` recovers a worker, increment `dispatch_generation` and reset **all** dispatch fields in the same guarded job update. Terminal jobs need no further dispatch.

Dispatch bookkeeping changes do not increment the job's UI `sequence`. A publish confirmation belongs to the generation and lease token used for that attempt. A delayed confirmation for an older generation, or for an expired and replaced lease, changes no fields. Permit a confirmation after the worker has already changed the same generation to `running`; the claim can race ahead of the publisher's database update.

## Target flow

1. `upload_pdf` commits the document and queued job in one SurrealDB transaction and returns the existing `202` response. The API does not publish to RabbitMQ. The new job row is the durable dispatch request, including when the API crashes immediately after commit or RabbitMQ is unavailable.
2. The background `knowledge-dispatcher` opens a SurrealDB live query on `job` using a separate connection, then scans for due work. Each job-change notification coalesces into another scan; the notification payload does not decide what to publish. Scan queued jobs with `dispatch_published_at IS NONE`, a due `next_attempt_at`, a due `dispatch_next_publish_at`, and no active dispatch lease. Claim one row with a guarded atomic update and a unique lease token. On live-query disconnect, keep dispatching from bounded reconciliation scans while retrying the subscription; resubscribe and scan again after reconnect. Also scan on startup and after broker reconnection so a missed notification cannot strand a committed job. Schedule a wake for the earliest future `next_attempt_at`, `dispatch_next_publish_at`, or dispatch-lease expiry instead of relying on a new database change at that time.
3. The atomic lease claim increments `dispatch_publish_attempts` once for that attempt. The claimant publishes a persistent `{job_id, dispatch_generation}` message to the existing queue and waits for RabbitMQ publisher confirmation. On confirmation, it sets `dispatch_published_at` and clears the lease/error/retry fields with a generation-and-token guarded update. On failure or timeout, it records a bounded error string, sets exponential-backoff `dispatch_next_publish_at`, and releases the lease. Set the lease duration above the broker confirmation timeout plus database-update margin; an expired lease remains recoverable.
4. The worker consumes and acknowledges as it does now. Its existing guarded `claim_job(job_id, dispatch_generation)` rejects duplicates, stale generations, and jobs whose retry time has not arrived. A broker confirmation whose database update fails may cause a duplicate publish later; that case is expected and safe.
5. Each API instance subscribes to `job` changes and forwards sequenced job snapshots to its existing `/v1/ws/jobs/{job_id}` clients. A new WebSocket connection and a fresh page load read the current job directly; `GET /v1/jobs/{job_id}` also repairs gaps after a WebSocket or live-query disconnect. Dispatch bookkeeping leaves `sequence` unchanged, so it does not produce a new progress snapshot. The browser ignores stale sequence numbers and stops following a terminal job.

## Implementation sequence

1. Add the job fields and a useful due-dispatch index. Add a one-time, versioned backfill for every existing row missing the new required integer fields: preserve any existing `dispatch_generation`, otherwise set it to `1`; set `dispatch_publish_attempts = 0` and the optional dispatch fields to `NONE`. Only queued rows then need dispatch; running and terminal rows still need the required fields so future updates pass schema validation. The backfill skips already migrated rows, because clearing a confirmed timestamp would trigger another publish. Do not infer that an existing outbox `published_at` covers a newer `dispatch_generation`.
2. In `app/infrastructure/surreal.py`, add a `job` live subscription that closes cleanly and exposes changed job IDs for the API; the dispatcher may ignore the payload and use notifications only as wake-up hints. Verify the installed SurrealDB SDK's notification shape in a live test. Add bounded due-job selection and an atomic per-job dispatch claim, plus generation-and-token guarded success/failure updates. Handle transaction conflicts using the existing claim retry pattern. Update job creation, retry scheduling, and expired-lease recovery to maintain the invariant above. Remove outbox database methods and the outbox live subscription after callers have moved.
3. Give `RabbitMqBroker` a focused `publish_job_trigger(job_id, dispatch_generation)` operation using the current durable queue, persistent message, mandatory routing, and publisher confirmation. Remove status-message publishing and `publish_outbox_event` after callers have moved.
4. Replace `app/outbox.py` with a `job-dispatcher` process. Establish the `job` subscription before the initial scan to close the startup race; if subscription setup fails, scan anyway and keep retrying subscription. Coalesce live-query notifications into scans, claim due jobs, publish them, and reconnect after database or broker failure. Continue bounded reconciliation scans while subscribed or disconnected, after subscription reconnects, and after broker reconnects. Use a timer for the next scheduled retry, queued job due time, or expired dispatch lease. A self-generated dispatch update may trigger a notification; eligibility filters and wake coalescing must prevent a publish loop. Remove the direct publish path from `api/v1/documents.py`.
5. Keep `app/worker.py` RabbitMQ admission and worker lease recovery. Update its comments and recovery path so a requeued job becomes eligible for the dispatcher. Ensure `job.type` still comes from the claimed database record, preserving shared-queue routing.
6. Replace the API's RabbitMQ status subscription with one SurrealDB `job` live subscription per API instance on a separate connection. On a notification for a job with connected clients, read its authoritative row, convert it through the existing `JobStatusResponse` mapping, and broadcast it through the status hub; never send dispatch bookkeeping or sensitive job fields. Keep the WebSocket endpoint, its authorization, heartbeat, and sequence check. Start the subscription before accepting WebSocket clients; if it is unavailable, let the API serve REST while clients use REST fallback. Close active WebSockets when the live query disconnects so clients switch to REST recovery. On reconnect, resubscribe and refresh active jobs from the database. Update `apps/admin-web/src/features/knowledge/hooks/useIngestionJob.ts` to read an initial REST snapshot, use WebSocket updates when available, and poll REST every three seconds while disconnected; retry after an initial REST failure. Reset its stored job and sequence when `jobId` changes. Remove the RabbitMQ status exchange and RabbitMQ status-event payload code only after database-backed live updates work; preserve the WebSocket status payload.
7. Replace the `knowledge-outbox` Compose service with `knowledge-dispatcher`. Update settings, metrics, health checks, README, and workflow docs to describe live-query connection state, pending dispatches, leases, publish errors, and delayed retries. Change API `/ready` to require the database and object store, not RabbitMQ: committed uploads must remain available during a broker outage, and the API no longer holds a RabbitMQ status connection. After all callers have moved, add an explicit SurrealDB migration to remove `job_status_outbox` and `job_dispatch_outbox`; deleting their `DEFINE EVENT` lines from the schema file alone does not remove installed events. Stop new outbox writes before removing the outbox table definition. Retain existing outbox rows until cutover has been verified, then archive or delete them in a separate cleanup step.

## Verification

- A job committed just before an API crash is published when the job live query wakes the dispatcher or its startup/reconciliation scan finds the row. A RabbitMQ outage leaves it queued and unpublished; broker recovery causes confirmed delivery. The API returns `202` and stays ready while RabbitMQ is unavailable.
- A queued job committed while the dispatcher live query is disconnected is published by a reconciliation scan. Subscription reconnect triggers another scan. A future worker retry, publish retry, or expired dispatch lease is published when due without requiring a new notification. Job progress updates and dispatcher bookkeeping do not cause repeated publish attempts.
- Two dispatcher instances racing for one job produce one active lease. Lease expiry allows takeover. A late success or failure from the old token or generation cannot overwrite current dispatch state.
- RabbitMQ accepts a message but confirmation or database marking fails: a later duplicate publish is harmless, and only one worker can claim the generation.
- A worker retry and an expired worker lease each increment the generation, clear `dispatch_published_at`, and cause a new trigger at the correct time. Old queued messages are acknowledged without running the new generation.
- The UI receives live progress from database-backed WebSockets without RabbitMQ status events. A client joining or reconnecting reads the latest job row; a dropped WebSocket falls back to REST and reaches terminal state. Changing job IDs resets the sequence guard.
- Run the knowledge-service unit/integration suite and frontend tests, plus a Compose smoke test with API, dispatcher, worker, SurrealDB, and RabbitMQ. Check the existing shared queue name and message routing in the live test.

## Cutover and completion

Roll out the additive job schema first. Start the new dispatcher before retiring the old outbox publisher; brief duplicate sends are safe because claims are generation guarded. Deploy the API's database-backed WebSocket publisher and updated frontend, then stop the outbox publisher and run the event-removal migration once no old API or worker replicas depend on it. Do not purge or rename the RabbitMQ queue. Inspect queued jobs, active dispatch leases, publish errors, live-query reconnects, WebSocket recovery, and queue depth through a full retry and worker-recovery cycle before considering the migration complete.

The accepted tradeoff is that a live query can miss intermediate progress while disconnected. The job row remains the current truth; initial snapshots, reconnect refreshes, and REST fallback restore the latest state without maintaining durable status events.
